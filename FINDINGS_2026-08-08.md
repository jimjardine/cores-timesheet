# Pre-Launch Code Review — 2026-08-08

Full codebase sweep across DB/schema, SMS/WhatsApp/email comms, frontend, and payroll/build. 7 Sonnet 5 agents reviewed disjoint areas; every medium+ severity finding was then adversarially re-verified by a separate agent that re-read the actual file before being included here (0 findings dropped for the per-area cap; a handful were refuted and excluded). Low-severity findings were not sent through verification — read those with a bit more skepticism.

**32 confirmed findings** (6 critical, 10 high, 16 medium) + **5 unverified low-severity notes**.

---

## CRITICAL

### 1. RLS policies are `USING (true)` on effectively every Cores table
`supabase/migrations/20260713170000_audit_log_readonly_policy.sql:5` (and repeated across `job_supplies`, `gear_photos`, `weekly_summary_posted`, etc.)

The public anon key — shipped in the frontend bundle — has full read (and on most tables write/delete) access to all business data at the database level, with no server-side admin check. Anyone can call the Supabase REST API directly with the anon key and read the full `audit_log` (PII, pay-rate config, deleted rows) or mutate `payroll_config`/`timesheet_entries`, bypassing whatever gating exists only in the React UI. Flagged before as a known tradeoff (backlog #12) but remains a real, exploitable hole in a client-facing production app.

### 2. Twilio webhook has no enforced auth; JSON path has none at all
`supabase/functions/sms-timesheet/index.ts:171`

Signature validation is computed and logged but never checked at the call site (line 745). `verify_jwt` is disabled on the function. Anyone who knows the function URL can POST fabricated `{from_phone, body}` JSON with zero credentials and inject fake hours attributed to a real employee, silently delete a pending submission (`body:"reject"`), or read any tech's day/phone directory.

### 3. Employee login issues no signed session — client self-reports identity
`supabase/functions/employee-auth/index.ts:196`

Login returns `{ id, name }` with no JWT/cookie, stored verbatim in `localStorage`. Every downstream query goes through the anon Supabase client with only a client-controlled `.eq('employee_id', ...)` filter — no RLS restricts by employee. Editing `localStorage` to another employee's UUID grants full read/write/delete over their real timesheet data, no PIN/OTP required.

### 4. PasswordGate is not real authentication
`src/components/PasswordGate.jsx:3`

Hardcoded plaintext password (`'Cores'`) visible in the shipped JS bundle; `localStorage.setItem('cores_unlocked','true')` bypasses it entirely. Moot anyway since the same anon key has full CRUD via RLS (see #1). If the team believes this is "the admin login," that belief is false.

### 5. Employee session is an unsigned client object — full impersonation
`src/employee/EmployeeApp.jsx:11`

Same root cause as #3, confirmed independently from the frontend side: `getSession()`/`handleLogin()` trust whatever's in `localStorage` with no server round-trip. Editing the stored session object impersonates any employee across `EmployeeHome.jsx`, `EntryForm.jsx`, `PendingEntryEdit.jsx`.

### 6. Weekly overtime threshold is dead code — silently underpays OT
`src/utils/entrySave.js:17` (root cause; also independently surfaced via `src/components/Reports.jsx:301` — see #12)

`computeDailyOTSplit`/`fetchDailyOTContext` stamp a concrete (non-null) `ot_hours` on every entry at save time using only that day's hours. `otCalc.js`'s `computeOTMap` treats any non-null `ot_hours` as manually-set and skips its own weekly-40hr-threshold logic. Result: an employee working 42 hrs across 6 days (7hrs/day, each under the daily-8 threshold) shows **0 OT** everywhere — Reports, AdminDashboard, EmployeeHome, PDFs, CSV exports — instead of the 2 hrs of weekly OT the app's own configured rule calls for. This affects every entry created through the normal app flow, not an edge case.

## HIGH

### 7. A live migration wipes all customer/job/vessel/timesheet data
`supabase/migrations/20260707000000_update_thales_jobs.sql:4`

Unconditional `DELETE FROM timesheet_entries, jobs, vessels, customers` before reinserting a fixed Thales-only fixture set, with no environment guard, permanently in migration history. If ever replayed (staging branch from a prod clone, `supabase db reset`, migration repair), this destroys all business data down to ~40 hardcoded July fixtures.

### 8. Pending manual-entry confirmation treats ANY reply as "yes"
`supabase/functions/sms-timesheet/index.ts:1163`

No affirmative-reply check. A tech disputing a manual entry ("no that's wrong, I was on 4900") gets it marked `confirmed` with the dispute buried in a text field. A stale unresolved pending-confirmation can also swallow an unrelated, genuine new timesheet text entirely.

### 9. Single-job submissions get hours silently overwritten by time-bounds math, defeating the mismatch flag
`supabase/functions/sms-timesheet/index.ts:1401`

When a submission collapses to exactly one job entry, its stated hours get replaced by a time-in/time-out calculation — even when the tech explicitly stated different hours in a separate message — and this recomputation also zeroes out the delta that would normally flag the mismatch for review.

### 10. `set_pin` OTP has no rate limit or lockout
`supabase/functions/employee-auth/index.ts:164`

Unlike `login` (which tracks `pin_fail_count`/`pin_locked_until`), `set_pin` never throttles guesses. An attacker can brute-force the 6-digit OTP (1M possibilities) within the 10-minute TTL and take over the account.

### 11. Reassigning an entry's employee/date overwrites the target's real supplies
`src/components/AdminDashboard.jsx:213`

`saveEdit()` deletes ALL `job_supplies` rows for the *new* employee/date and replaces them with the *original* entry's supply list. Correcting a misattributed entry can silently destroy another employee's real supply records for that day.

### 12. Same weekly-OT dead-code bug, independently found from the Reports side
`src/components/Reports.jsx:301` — duplicate root cause of #6, confirms the bug is visible (and silently wrong) across every reporting/export surface, not just entry creation.

### 13. SMS approval has no concurrency guard — can double-insert a day's hours
`src/components/SmsReview.jsx:179`

`approve()` has no `.eq('status','submitted')` precondition and no unique constraint linking `timesheet_entries` back to the submission. Two admins approving the same submission within about a second of each other both succeed, duplicating that day's hours/OT with no trace to dedupe after the fact.

### 14. Tagging a photo against a closed job silently orphans it forever
`src/components/GearPhotos.jsx:57`

Job lookup for manual tagging only includes `status='open'` jobs. Tagging a photo for a since-closed job writes `job_id: null` while also marking it no longer "pending" — it vanishes from both the review queue and every Reports view with no error.

### 15. "+ Add job" always marks new hours as regular time
`src/utils/entrySave.js:67`

`addJobToDay` (used by EmployeeHome's "+ Add job") sets `ot_hours: 0` unconditionally, ignoring hours already logged that day — unlike the correct path in `EntryForm.saveNewDay`. Real overtime silently becomes straight time.

### 16. Stat pay can be double-granted under concurrent saves
`src/utils/statPay.js:43`

`ensureStatPay` does a check-then-insert with no unique constraint or locking. Two independent save paths racing (e.g. admin approving an SMS submission while the employee saves via self-service) can both pass the "no existing stat entry" check and both insert, doubling stat pay for that day. Same bug class as the SMS/WhatsApp race already fixed once in this codebase.

## Suggested priority order before client launch

1. **#6/#12 (weekly OT dead code)** — this is actively mispaying employees right now, on every entry, not a hypothetical.
2. **#1, #3, #5 (RLS + no real session)** — these three are one underlying problem: there is currently no real server-side access control anywhere in the app. Worth deciding as a single design conversation (real Supabase Auth + row-level RLS keyed to `auth.uid()`) rather than patching each symptom.
3. **#2 (unauthenticated webhook)** — payroll-integrity and PII risk reachable by anyone who finds the function URL.
4. **#7 (data-wiping migration)** — cheap to fix (delete the file or guard it), high blast radius if ever triggered.
5. **#13, #16 (race conditions)** — same bug class already fixed once for SMS; worth a shared fix pattern (unique constraints + conditional updates) rather than one-off patches.
6. Everything else, roughly in the medium/high order above.
